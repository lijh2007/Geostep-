# 0.4.8：测试反馈修复核验

发布版本：主应用 0.4.8 / 模块 0.3.15 / 内置 Root 载荷 0.1.4。

## 反馈与证据

- 截图显示“未检测到模块、已安装未知、系统加载 0.3.14”。旧代码将包管理器查询失败当作未安装，同时要求安装版本与已加载版本相等，造成已收到有效系统回执仍被拦截。这个分支可以从代码和回归测试确认。
- 另一张诊断截图为主应用 0.4.6、荣耀 BVL-AN00、Android 17 / API 37，安装模块 0.3.14，但没有系统回执。不能将它等同于前一张“已有加载版本”的故障，也不能据此认定没勾选 LSPosed。
- 用户另报 ColorOS 17 的 Root 坐标跳动、自定义 su 不可用，以及真我 Neo7 打开其他应用后重启。未提供提权工具调用约定或重启堆栈，暂不能确认这些故障的具体根因。

## 实现

- 模块安装与版本检查合并到引擎握手中。存在新鲜的有效加载回执时，安装包版本不可见只作说明，不再阻止模拟。已知的安装/加载版本不一致、过旧版本、无回执和钩子不完整仍阻止启动。
- 新模块提供包含版本、进程、钩子状态、修订号等字段的完整命令回执。主应用按随机请求标识、运行模式、时效和字段完整性核验；Provider 不可用时可使用该回执。旧模块仍走原 Provider 通道。`pong=true` 本身不能判定可用。
- Provider 回写按调用者所在 Android 用户空间寻址，不再始终写到用户 0 的主应用。此项多用户故障机实测待完成。
- 自定义 su 新增自动、`-c`、标准输入三种调用方式。自动模式只用 `id` 探测调用方式；文件不可执行和授权超时不自动重试；部署和注入命令不因失败切换方式重放。标准输入保留命令退出码，有读写超时与输出长度限制。提权程序仍需可执行、允许本应用访问并实际返回 uid=0。
- 普通应用钩子禁止进入共享系统 UID、隔离 UID 和 SDK 沙箱。厂商系统包只在确认本进程具有真实的本地定位服务时安装系统钩子，不依赖厂商包名白名单。
- 无关 AppOps / Settings 查询直接返回原结果，不执行额外配置或豁免查询。豁免查询不再持有本模块锁调用包管理器/系统权限服务，减少与系统服务锁形成反向等待的风险。

- 构建与 Lint 通过；165 项 JVM 测试通过：model 25、engine 54、data 9、module 65、app 12。覆盖包不可见但已加载、旧/错误回执拒绝、自定义 su 协议选择及不重放部署命令、系统 UID 保护等分支。
- 通用 Release 主包 39,145,837 字节，签名与正式版一致，ARM 32/64 位齐全，无私人地图 Key。Root 原生加载段与 0.4.7 相同。
- 小米 15 / Android 16 / API 36：主包 0.4.8 升级、启动与设置保留通过。设置界面分别选择默认 `-c` 和标准输入，两者实际返回 uid=0。
- 自定义 `/system/bin/su` + 标准输入在主应用中返回 uid=0；`/system/bin/sh` 被正确拒绝。绝对路径测试由脚本写入本应用测试设置，再从真实界面执行授权检查；不把 ADB 键盘输入路径的尝试算作通过。
- 相同主包配合当时已加载的 **模块 0.3.13**：60 秒持续定位通过，GPS 60、network 80、fused 117 帧更新，最大间隔 1,015 ms；系统接口、WebView、PendingIntent、取消、注销、flush 与 STOP 检查通过。这是主包在旧模块上的回归；新模块 0.3.15 的结果见下节。
- 对模块 0.3.15 APK 在独立 Android 进程中实测：无 ActivityThread/应用 Provider 时仍生成 22 字段完整回执，并通过 Parcel 序列化往返。该测试不等于故障 ROM 的实际 Binder 通道已通过。
- 从同一主包提取 Root 0.1.4，在自有独立进程中加载，8 项 ART 测试通过；系统进程未重启。该测试不等于纯 Root 系统接管通过。
- 验收后恢复全部原设置、停止模拟，完整安装模块 0.3.15 并校验设备 APK 摘要。当时 `system_server` 仍为 PID 3528，新模块等待用户手动重启。其他模块和热点配置未修改。

## 2026-11-03 重启后验收

- 用户手动重启后，新系统进程 PID 3518 实际加载 **0.3.15**，钩子回执为 `ready (23)`。主应用运行环境也显示安装和加载版本一致、系统通道及钩子就绪。
- 精确候选主包 `b7084cbd…` 配合新模块完成 **180 秒**持续定位：GPS 180 帧、network 239 帧、fused 354 帧，共 **773 帧更新**，最大间隔 **1,030 ms**；坐标、provider、模拟标记检查无错误。一次性定位、WebView、PendingIntent、取消、注销、flush 与 STOP 均通过。
- 同签名临时验收工具只使用 Android API，直接在已安装 Release 主应用中验证 PING / SET（保持停止状态）/ GET_STATUS / STOP。四条命令均返回完整回执，随机请求标识、后端、版本、PID、时效和钩子状态一致；正常 Provider 通道也通过。
- 临时关闭**本应用的状态 Provider 组件**，确认该通道不可达后，四条命令仍通过直接回执返回。此条件下，真实主应用再完成 **20 秒、84 帧更新**及生命周期/停止测试。随后组件恢复原始默认状态，再次核验 Provider 回执可用。其他应用组件未修改。
- GNSS 状态、NMEA 校验和与一致性、六类传感器、动态豁免/取消豁免、停止/重启模拟、订阅恢复与注销后无残留回调均通过。
- 全程 `system_server` PID 保持 3518，没有系统重启。原设置和豁免文件恢复，模拟停止，临时验收 APK 已卸载；已有独立探针和其他定位模块保留原状态。
- 收尾修正诊断导出的旧文案：包信息查询失败显示“无法查询”，不再直接断言“未安装”。此项仅修改主应用诊断文本，不需要再次重启系统模块。
- 文案修正后的最终主包已重新通过主应用单测、Release 构建和 Lint，并覆盖安装。最终 APK 的 20 秒定位与生命周期/停止复查通过；Root 资产和原生库与本轮完整测试包逐字节一致，模块 APK 未变。

这些结果来自小米 15 / Android 16，已有其他定位模块保持启用，不是隔离其他模块后的对照结论。多用户回执寻址与 Android 17 原故障机仍待验证。

发行文件归档在 `releases/github-v0.4.8/`，仅主应用、模块及 SHA256SUMS，使用已验收的最终候选原文件。最终主包 **39,146,009 字节（约 39.15 MB）**，SHA-256：`cb1148b4727d4dfbc40588ce6f2e46871f9d8bf8f48026812f5525aeb6897681`；模块：`c68afdff5159c3a453cd9e62ef3961bfbe0af3c61fafd0733612717606a5b085`。

## 验收边界

以上稳定性改动不等于已复现或修复真我重启。需要故障机重测或系统崩溃证据才能确认。ColorOS 17 Root 跳动、荣耀无回执和具体临时 Root 工具兼容性也不能由小米 Android 16 的通过结果代替。

Root 0.1.4 的纯 Root 系统接管尚未在无 LSPosed 驻留的环境单独复测。标准模式首个缓存 GPS 回调标记的干净环境对照仍未完成，沿用 [0.4.7 的限制](VERIFICATION_0.4.7.md)，本版不宣称该问题已解决。

保持已有定位模块与热点配置，不自动重启。测试包及内部诊断文件不加入普通用户 Release。
